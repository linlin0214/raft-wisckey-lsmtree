#  Raft-WiscKey-LSMTree

[![C++ Standard](https://img.shields.io/badge/C%2B%2B-17-blue.svg)](https://en.cppreference.com/w/cpp/17)
[![Linux Platform](https://img.shields.io/badge/Platform-Linux%20%7C%20x86__64-orange.svg)]()

基于 **C++17** 独立构建的高性能、强一致性分布式 Key-Value 存储引擎。系统底层由 **Raft 分布式共识协议** 与 **WiscKey / LSM-Tree 存储引擎** 构成，结合自研基于 Linux `Epoll` 的单线程非阻塞 Reactor 网络框架，实现了万级 QPS 下的高并发事务提交、毫秒级故障自动切主与零数据丢失（RPO = 0）。

---

##  系统架构全景

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                           Client / Application                              │
└──────────────────────┬───────────────────────────────┬──────────────────────┘
                       │ (自研二进制协议 988x)           │ (RESTful HTTP 808x)
┌──────────────────────▼───────────────────────────────▼──────────────────────┐
│                    Network Layer (Non-blocking Reactor)                     │
│  • Linux Epoll + EventLoop 驱动       • 动态双缓冲区 + EAGAIN 优雅处理      │
│  • 定长包头+变长包体协议 (解决粘包)    • timerfd 高精度 Tick + eventfd 跨线程唤醒 │
└──────────────────────┬──────────────────────────────────────────────────────┘
                       │ (微秒级内存消息投递)
┌──────────────────────▼──────────────────────────────────────────────────────┐
│                      RaftCore (纯内存共识控制面)                             │
│  • Quorum 快速仲裁与 No-op 日志       • Pipeline 连续追发 + 动态 Conflict 回退 │
│  • 随机选举超时 (500~1000ms) 防抖动   • 未提交日志高水位拦截背压 (防 OOM)    │
└──────────────────────┬──────────────────────────────────────────────────────┘
                       │ (Ready 管道异步投递)
┌──────────────────────▼──────────────────────────────────────────────────────┐
│                   Storage Engine (Group Commit Pipeline)                    │
│  • 专职 StorageThread 批次合并        • 单次 fdatasync 聚拢 20+ 条日志落盘   │
│  • WiscKey 键值分离 + LSM-Tree 存储   • 日志条数 / 时间双维度自动化 Snapshot │
└─────────────────────────────────────────────────────────────────────────────┘
 核心技术特性高性能非阻塞网络引擎：基于 Linux Epoll 构建单线程 Reactor 事件驱动模型，屏蔽物理 I/O 阻塞。设计 15 字节大端定长帧头与 Magic 魔数滑动探针，妥善解决高并发打流下的 TCP 粘包、半包与脏数据容错；引入 readv 栈两段式散列读，大幅减少内存动态扩容。使用 idle_fd 机制防御 Linux EMFILE 套接字描述符耗尽引发的 CPU 伪空转。纯内存共识状态机：共识计算耗时控制在 1 µs 以内，将心跳周期定为 50ms，选举超时区间调优至 500ms ~ 1000ms，有效抵御底层磁盘刷盘抖动，杜绝网络假死导致的误切主。支持 No-op 保护日志推进、Conflict Index 快速回退，并在 3 节点场景下引入无内存分配的 Quorum 中位数计算。微批与组提交（Group Commit）落盘：设计专职异步落盘线程（StorageThread），将队列中积压的多个 Ready 自动聚合为超级 WAL Batch，一次性调用物理 fdatasync() 完成多条日志落盘，突破物理磁盘 IOPS 瓶颈。端到端背压与稳定性防护：在客户端入口设置未提交日志高水位线（10,000 条），写超载时主动返回 REJECT 拒绝，常驻内存安全锁定在 120MB 以内，彻底避免 Linux 内核 OOM Killer 强杀风险。全链路可观测性与实时看板：内嵌轻量级 HTTP 监控门面，提供可视化 Web 控制台，实时呈现节点角色（Leader/Follower）、Term、CommitIndex、StabledIndex 及 WAL 刷盘时延。 基准压测数据 (Benchmark)在 3 节点集群全量开启 fdatasync 物理刷盘、4KB 载荷并发灌入场景下的压测表现：指标维度测试结果备注并发线程数8 线程模拟高并发客户端持续打流Payload 大小4,096 Bytes (4KB)典型 KV 大载荷场景有效吞吐 (QPS)~3,000 ops/s纯单盘物理持久化场景物理网络带宽11.71 MB/s接近单盘饱和带宽P50 延迟64.04 ms端到端 Quorum 提交延迟P90 延迟130.33 ms包含偶发磁盘 I/O 争抢排队事务完整性90,000+ 笔 100% 成功零丢包、零错乱 (RPO = 0)
